01 Overview

I already wrote about why this project treats a grid cell as a rule-bearing design unit rather than a maze-specific trick — Controlled Procedurality. This post is the concrete system behind that idea: what actually ships, node by node.

It's a procedural generator for multi-floor mazes and dungeons. One Houdini Digital Asset deterministically builds topology (rooms, a DFS-graph of corridors, entry/exit), geometry (walls, floors, ceilings, wall-end caps, openings), and gameplay content (doors, keys and locks, chests, traps, enemies, loot, decorative prop scatter), then hands all of it to Unreal as one unified stream of points. C++ on the Unreal side turns those points into real HISM instances and spawned Actors.

The core idea of the whole project: Houdini is the only source of truth — topology and placement logic. Unreal is a thin consumer — it interprets already-computed points and makes no decisions of its own. Between them, exactly one contract: PLACEMENTS_V1.

02 Two layers, one contract

Inside the HDA itself, the graph isn't one flat network — it's 144 top-level nodes (plus the sub-networks inside foreach/repeat blocks), organized into sequentially numbered stages (00_ through 30_) mixed with unnumbered branches — registries, debug views, the prop system, and presets were added later and were never folded back into the numbered sequence. Almost none of the logic actually lives in SOP nodes; it lives in Python, and the network nodes are mostly thin wrappers around shared modules.

Generation (topology)
├─ Structural geometry  → Ground, Walls per floor, Wall Ends/Caps, Openings, Ceiling
├─ Gameplay              → Lock/Key, Door/Chest/Trap/Enemy/Loot/Key scatter
└─ Props                 → Ground prop candidates → scatter
        │
        ▼
   PLACEMENTS_V1 (unified transport)
        │
        ▼
Houdini Engine for Unreal → MazeHoudiniDataConsumer (C++)
        ├─ structural → HISM / Actor  (walls, floor, caps)
        ├─ gameplay   → Actors        (doors, keys, enemies)
        └─ prop       → HISM / Actor  (decor: StreetLight, etc.)

03 Principles that repeat everywhere

A handful of decisions show up at every level of the project. Worth knowing before reading any specific stage.

Registry before consumer

Three registries — Module, Gameplay, and Props — normalize into one node, 01_DATA_REGISTRY, right at the start of the graph. Every scatter system reads that registry, either through a direct SOP input or an explicit out-of-band cook — always after it's already computed.

Manual / Random / Both — one authoring pattern everywhere

Nearly every placement system (Room, Door, Chest, Trap, Enemy, Loot, Key, Open Passage, Wall Vertical Override, Ground Prop Scatter) offers the same choice: place a point by hand, scatter randomly by rule (Step / Probability / Min Distance), or both at once — Manual rows are placed first, then Random fills in the rest around what's already occupied.

Stable keys, not indices

An index into an array isn't an identity — order can change. Every placement system has a deterministic string key instead (connection_key, wall_column_key, gpcand:cell{i}:x{x}:z{z}) — usually a source id combined with a rounded position. Manual rows get both: an index for convenience and a locked_*_key for stability. If the locked key is empty, resolution falls back to index, but the diagnostic always logs the real resolved key so it can be copied in and pinned.

Deterministic RNG on string keys

Not Python's hash() — it's randomized between processes. A custom polynomial hash is recreated locally in every module that needs it. Every independent "target" of randomness (accept/reject a candidate, position, rotation, scale, representation choice) gets its own RNG stream, so changing one parameter doesn't reshuffle everything else.

One transport to Unreal

Three sources of placements, but exactly one JSON array of points goes out, on one schema — not three separate outputs. See §05.

Never edit production directly

Every change goes through a numbered candidate copy, checksums before and after, a clean smoke test, a full regression run, and an explicit, confirmed production update.

04 The pipeline, stage by stage

At a summary level — later posts go deep on the stages that have the most interesting history.

Topology

Grid → Registry → Room → DFS → Entry/Exit. The DFS tree is the only source of connectivity for everything downstream — wall geometry and Lock/Key progression are both built on the same graph, guaranteed cycle-free outside explicitly allowed Loop Chance edges.

Ground and walls

One point per floor cell, classified by topology (dead-end, straight, corner, T, cross) and assigned a module variant from weighted pools. Walls were originally one flat 2D network for the whole building, with "floor" reconstructed after the fact by guessing a Y-range — a third-party black-box tool processed the whole building height in one pass. Different floor heights broke that guess. The fix was genuinely per-floor generation, with a fixed limit of 6 slots per floor built into the graph itself — a deliberate compromise around a third-party node with an unclear multi-floor cook contract. That story gets its own post.

Openings

Door and Open Passage share one model: pick a connection point, then pick what happens at it. The point itself isn't floor-specific — the carve is replicated per enabled floor afterward, splitting the nearest wall segment into up to five pieces (remainder / turn / opening / turn / remainder), a shape the existing wall-end classifier recognizes on its own as two new terminal edges. Also its own post.

Gameplay

A deterministic Entry → Key1 → Door1 → … → KeyN → DoorN → Exit sequence, built over verified bridges of the same DFS tree — the mechanism behind the reachability guarantee described in the previous post. Seven independent Manual/Random/Both systems (Room, Door, Chest, Trap, Enemy, Loot, Key) merge into one gameplay placement stream.

Ceiling and props

Ceiling modules mirror the ground pass, with a per-floor toggle. Decorative prop scatter (the first example is StreetLight) follows ground paths through the same candidate → classify → scatter → registry-lookup structure as everything else — one more instance of the same repeated pattern, not a separate system.

05 One transport: PLACEMENTS_V1

All three sources of placements merge into one node:

OUT_STRUCTURAL_PLACEMENTS_V1  (direct SOP input)
OUT_GAMEPLAY_PLACEMENTS_V1    (out-of-band cook+read by node name)
OUT_PROPS_PLACEMENTS_V1       (out-of-band cook+read by node name)
        │
        ▼
   15_PLACEMENTS_V1  →  OUT_PLACEMENTS_V1  →  output0

This isn't a generic domain dispatcher — the three sources are hardcoded explicitly: three converters, three literal placement_domain values (structural / gameplay / prop). The shared point schema is one flat dictionary of defaults where every domain's fields coexist; adding a new domain means a new block of fields in that same dictionary, not a new schema.

06 From an 8,130-line monolith to 66 modules

All the logic used to live in one PythonModule Extra Section — 8,130 lines at its peak. It's now 66 modules under one maze.* namespace, assembled by a build script from a manifest file: maze.core, maze.generation, maze.structural (16 modules — the largest group), maze.gameplay (13), maze.registry, maze.props, maze.presets, maze.debug, and maze.integration. A hand-maintained facade wraps each callable entry point; the node scripts themselves are almost all one-line calls into the module that actually does the work — a node's name is usually a direct pointer to which function is behind it. That migration, and the two loader bugs it surfaced, is its own post too.

07 What's next

This post is the map. The territory gets covered one piece at a time: per-floor wall generation and the 6-slot constraint, the Door/Open Passage carve pipeline, the Lock/Key reachability algorithm in full, the Python architecture migration in detail, and the preset system that lets a new UI parameter reach a save file without touching serializer code.

08 Current scale

144 top-level nodes, 66 Python modules under maze.*, five top-level UI tabs, one unified output contract covering three placement domains. Built and maintained by one person — which is the entire reason every principle in §03 exists: none of this stays legible without them.
